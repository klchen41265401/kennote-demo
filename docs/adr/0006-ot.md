# ADR 0006：自建簡化版 OT（M6 第 1–5 項）

- 狀態：已採用（M6），**預設關閉**（`FEATURE_OT=false`）
- 日期：2026-09-19
- 相關規格：**04 §6.6 全部**（§6.6.1–§6.6.6）、04 §8 M6 第 1–5 項、04 §9.3；
  03 §8.4（Phase 3 OT 資料層）；01 §6.1（5×5 轉換矩陣）
- 前置決策：ADR 0001（全自研核心）、ADR 0002（RichText 模型）、**ADR 0004（M5 即時協作層 / LWW）**

---

## 1. 背景

M5 交付的是 04 §6.6 的**階段二**：block 粒度 LWW + 社交式避讓（presence、`baseVersion`
衝突提示、可從歷史還原）。已知限制寫在 ADR 0004 §4：

> 仍然是 block 粒度 LWW：兩人同時改同一段文字，後送的會覆蓋前者。

M6 要把文字層級升級成**階段三：自建簡化版 OT**，驗收標準是
「兩人同時編輯同一段文字，兩人的字都保留且順序合理」與
「A undo 自己的操作，不會影響 B 在同一 block 後來打的字」。

禁用清單不變（00-README 決策 #11 / `scripts/check-deps.ts`）：
**Yjs / Automerge / ShareDB / ot.js / Liveblocks 一律不用**。
本次實作**沒有新增任何 runtime 依賴**（`fast-check` 早就在 editor-core 的 devDeps）。

### 為什麼自建 OT 而不是 CRDT（04 §6.6 階段三的引文）

CRDT 的優勢是「不需要中央伺服器」，但**我們本來就有中央伺服器**。
在「中央權威伺服器 + 全序列化」的前提下，OT 只需要滿足 **TP1**，
**不需要** TP2 —— 而 TP2 正是 OT 惡名昭彰的難點。
去掉 TP2 之後，核心演算法約 150 行，可以自己寫對並測對。

## 2. 決策

### 2.1 資料模型：三種原子操作，atom 用 U+FFFC 佔位

`packages/editor-core/src/ot/types.ts`（前端權威）與
`packages/shared-types/src/ot.ts`（線路型別，結構相同）：

```ts
export interface MarkPatch { add?: Mark[]; remove?: Mark[] }

export type OtTextOp =
  | { retain: number; marks?: MarkPatch }          // 跳過 n 個字元（可順便改格式）
  | { insert: string; marks?: Mark[]; atom?: InlineAtom }  // 插入
  | { delete: number };                            // 刪除

export interface OtDelta { ops: OtTextOp[] }
```

**不變量：** 一個 delta 的 `retain + delete` 總和 <= 套用前的文件長度。
這個不變量讓 `transform` / `compose` 的正確性可以被驗證。

四個刻意的設計決定：

1. **單位是 code point，atom 佔 1**，與 `text/richtext.ts` 的 offset 完全一致，
   所以 `slice` / `length` 可以直接複用，不必另寫一套座標系。
   emoji（surrogate pair）也是 1。
2. **atom 用 `{ insert: '￼', atom }` 表示。** insert 永遠是字串（長度 1），
   所以長度計算、切片、transform 完全不必特別處理 atom；
   只有 `apply()` 在產生節點時才看 `atom` 欄位。
   好處：`invert` 可以把被刪掉的 mention/date 完整插回來（協作 undo 需要）。
3. **retain 可以帶 `MarkPatch`。** 否則「把兩個字變粗體」得表示成 delete + insert，
   與別人同時打字時 transform 的結果會很難看（會把對方插在中間的字吃掉）。
4. **型別不改 `operation.ts` 的 `TextDelta`。** 那是 M1 就定案、被 `Operation`
   引用的 wire 型別。`OtDelta` 在結構上**可以直接指派給 `TextDelta`**
   （只多了幾個 optional 欄位），因此 `text.delta` operation 一行都不必改。
   名字改叫 `OtDelta` / `OtTextOp` 只是為了避免同一個 package 匯出兩個同名型別。

### 2.2 `transform(a, b, priority)`：TP1，且 priority 必須成對使用

```
transform(a, b, false) → a'     （b 先、a 讓位）
transform(b, a, true)  → b'     （b 先、b 優先）

apply(apply(S, a), transform(b, a, true)) === apply(apply(S, b), transform(a, b, false))
```

**全專案的固定約定（伺服器與客戶端必須完全一致，否則永遠不會收斂）：**

> **已經被伺服器套用的那一邊 priority = true；還在飛行中的本地 delta priority = false。**

這條約定出現在三個地方，三處都照同一個方向寫：
`ot/client.ts` 的 `applyRemote`、`ot/transform.ts` 的 `transformAgainstAll`、
伺服器的 `ot-service.ts` 的 `receiveDelta`。

mark 衝突用同一條約定收斂：priority = false 的那一邊，
把「對方也碰過的 slot（b / i / link / color / comment:id）」從自己的 patch 拿掉。

### 2.3 `compose` / `invert` / `deltaFromDiff` / `transformCursor`

- `compose(a, b)`：`apply(apply(S,a), b) === apply(S, compose(a,b))`。client buffer 用。
- `invert(delta, base)`：`apply(apply(S,d), invert(d,S)) === S`。協作 undo 用。
  `MarkPatch` 的反向會**依 base 的節點邊界逐段還原**（範圍內格式不一致時才正確）。
- `deltaFromDiff(before, after)`：用既有的 `text/diff.ts`（共同前後綴）壓成最小 delta。
  這是「編輯器仍然產生整段新內容」與「OT 需要增量」之間的轉接點，
  **編輯器與 UI 一行不動**（04 §6.6.6 的承諾）。
- `transformCursor(offset, delta, isOwn)`：
  `isOwn = false` 時別人在我游標位置插字，我的游標**留在原地**（不被推走）；
  `isOwn = true` 時游標跟著跑到插入內容後面。對固定 delta 單調不減。

`DeltaBuilder.push()` 採 Quill 的正規化規則，其中一條特別重要：
**insert 永遠排在同位置的 delete 前面**，否則 `[delete 1, insert 'a']` 與
`[insert 'a', delete 1]` 會是同義但不同形的兩個表示法，等式比較會誤判。

### 2.4 Client 三狀態機（04 §6.6.3）

`packages/editor-core/src/ot/client.ts`，**純邏輯、零 DOM、零 I/O**，
一個 block 一個實例（block 之間的文字編輯本來就不衝突）。

| 狀態 | 本地編輯 | 收到遠端 | 收到 ack |
|---|---|---|---|
| `synchronized` | 送出 → `awaitingConfirm` | 直接 apply | （忽略重複 ack） |
| `awaitingConfirm` | 進 buffer → `awaitingWithBuffer` | 雙向 transform | → `synchronized` |
| `awaitingWithBuffer` | `compose(buffer, delta)` | outstanding 與 buffer 都 transform | 送出 buffer → `awaitingConfirm` |

`rev` 不連續時呼叫 `onDesync`（宿主重抓 snapshot），不硬套。

### 2.5 兩條通道，但**只有一個協定**

| 通道 | 內容 | 走哪裡 |
|---|---|---|
| delta 通道 | 同一個 block 內的**文字變更** | `text.delta` operation |
| tx 通道 | 結構變更（insert / delete / move / 換型別 / 改 props） | 原本的 `block.*` operation |

**關鍵決定：delta 通道不是第二套協定，而是既有 tx 通道上的一種 operation。**

- client → server：`submitDelta()` 包成一筆只有一個 `text.delta` op 的 `Transaction`，
  走原本的 WS `tx` 訊息（或 HTTP 降級），落到**同一支** `applyTransaction()`。
- server → client：ack 走 `txApplied`、廣播走 `txBroadcast`，
  伺服器把 transform 過的 delta 與新的 `rev` 放在 `TransactionResult.ops` 裡
  （這個欄位 M1 的註解就寫著「伺服器最終套用的 ops（可能經 transform 調整）」）。

因此 **`packages/shared-types/src/ws.ts` 一行都沒有改**，
DevTools 的 WS 分頁看到的訊息型別與 M5 完全相同。

唯一的差別是 delta **不進 300ms debounce buffer**：
OT 規定「同一個 block 一次只能有一筆 outstanding」，打包會破壞這個不變量。
delta 仍然會寫進 IndexedDB 離線佇列，斷線重送的行為與 tx 通道一致（txId 相同 → 伺服器冪等）。

### 2.6 兩條通道的順序一致性：`block.update{content}` 也推進 rev

這是最容易寫錯、也最容易被忽略的一格。

問題：兩條通道都會改同一個 block 的 `content`。如果 `block.update` 不推進 `rev`，
某個 client 用舊 `baseRev` 送來的 delta 會被套在「已經被整段覆蓋」的內容上，offset 全錯。

**簡化策略（本專案的決定）：**
`FEATURE_OT` 開啟時，`block.update{content}` 在伺服器端會被
`deltaFromDiff(before, after)` 壓成一個 delta，寫進 `block_deltas` 並 `rev + 1`。
廣播時也改用 `text.delta` 表示（型別 / props 的變更仍然是 `block.update`）。

於是**兩條通道永遠在同一條 rev 線上**，transform 窗口不會有洞，
client 的 `OtClient.rev` 也不會因為別人改了內容就對不上。

代價：一筆同時改 `props` 與 `content` 的 `block.update`，廣播時會變成兩個 op
（一個 `block.update{props}` + 一個 `text.delta`）。`splitDeltaOps()` 保證它們的
**相對順序不變**，宿主照著收到的順序套用即可。

### 2.7 Server：`receiveDelta` + `block_deltas` + `blocks.rev`

`apps/server/src/modules/blocks/ot-service.ts`，照 04 §6.6.4：

```
SELECT ... FROM blocks WHERE id = ? FOR UPDATE          ← 序列化的關鍵
SELECT delta FROM block_deltas WHERE block_id = ? AND rev > baseRev ORDER BY rev
逐一 transform(d, concurrent, priority = false)
content = apply(content, d)；rev = rev + 1
INSERT block_deltas / UPDATE blocks
回傳 transformed + rev（廣播出去的就是這一份）
```

三個補充決定：

1. **`blocks.rev` 是新欄位，不重用 `blocks.version`。**
   `version` 每次寫入都 +1（含 props / type 變更），而 `rev` 必須與
   `block_deltas` 的列一一對應，否則 transform 窗口會取到洞。
2. **`transform` 的實作與客戶端共用同一份**（`@kennote/editor-core`）。
   伺服器與客戶端各寫一份是 OT 最常見的死法 —— 兩邊算出不同結果就永遠不會收斂。
   `apps/server` 本來就依賴 `@kennote/editor-core`，不需要新增依賴。
3. **`page_transactions` 照舊每筆都寫**，但 `ops` 欄位存的是
   「最終 content 的 `block.update`」而不是 `text.delta`。
   這樣 M8 的版本歷史重播、斷線補傳、LWW 客戶端**完全不必認識 OT**。
   冪等仍然靠 `tx_id` 主鍵。

窗口被清掉（`baseRev` 太舊）時回 `CONFLICT`，請 client 重抓 snapshot，**不硬套**。

### 2.8 協作 undo：inverse delta 對後續遠端 delta 做 transform

M2–M5 的保守做法是「收到遠端 ops 就把受影響的 undo 紀錄丟掉」——
安全但難用（別人一打字我就不能 undo）。

M6 的做法：`HistoryEntry` 多一個 `deltas?: HistoryDelta[]`
（每個 block 一組 `{ forward, inverse }`）。收到遠端 delta 時，
`HistoryStack.onRemoteDelta()` 把 stack 裡同一個 block 的 forward / inverse
都對它做 `transform(..., false)`，順便把紀錄裡的 selection 用 `transformCursor` 推一下。

undo 時不再套用「當時記下的整段舊內容」（那會蓋掉別人後來打的字），
而是把已 transform 的 inverse delta 套到**目前**的內容上。

沒有 delta 表示的紀錄（結構操作、非 OT 模式）仍然沿用保守做法：丟掉那一筆與更早的。

### 2.9 客戶端的對稱規則：content **永遠**走 delta 通道

§2.6 只講了伺服器那一半。2026-09-20 的功能 QA（`docs/qa/functional-round1.md` BUG-4）
證明另一半也得補上：**客戶端也不可以讓 `content` 走 tx 通道。**

問題的形狀（實測抓到的 WS 訊框）：

```
1) text.delta  insert ">"                      baseRev 0   ← 打 ">"
2) block.update {blockType:"quote", content:[]}            ← markdown 規則（tx 通道，debounce 300ms）
3) text.delta  retain 1, insert " "                        ← 打空白鍵，被三狀態機 buffer 住，晚送
```

第 3 筆在語意上早就被第 2 筆整段覆蓋掉了，但它還握在 OT 客戶端手上，
之後才被送出去。伺服器照 OT 的規矩把它 transform 到最新版本（伺服器是**對的**），
於是空白鍵那一下被套回已經被覆蓋的內容上，前綴字元留在字尾（`> quote` → `quote>`）。
而且第 2 筆讓 `blocks.rev` 跳了一格，客戶端的 `OtClient.rev` 卻沒跟上，rev 線從此錯位。

**決定：`localOps` 送出之前，把每一筆「覆寫既有 block content」的 `block.update` 拆成兩個 op**
（`Editor.toWireOps()`，`packages/editor-core/src/core.ts`）：

| 原本 | 拆成 |
|---|---|
| `block.update { blockType, props, content }` | `block.update { blockType, props }`（tx 通道，LWW）<br>+ `text.delta`（OT 通道，帶目前的 `baseRev`） |

這與 §2.6 伺服器廣播時的拆法**完全對稱**（`splitDeltaOps()`），
兩個方向用同一組規則，所以不會再有「只有一邊認識 content 變更」的縫。

三個關鍵的細節：

1. **不是只有 content-only 的 `block.update`。** 舊版只在
   「沒動型別也沒動 props」時才 delta 化，於是 markdown 捷徑、`setBlockType`、
   Enter 分割（`block.update{content}` + `block.insert` 同一批）全部漏掉。
   現在只要 `patch.content !== undefined` 而且那個 block 在本地 doc 裡就一定拆。
   同一批裡「先 `block.insert` 再改它的 content」時，delta 的基準是**剛插入的內容**。
2. **順序必須維持。** 宿主用 `splitDeltaOps(ops)` 依原順序一組一組分流
   （`useEditorHost.ts`）：排在 delta 前面的 `block.insert` / `block.update{blockType}`
   要先進 tx buffer，`SyncClient.submitDelta()` 才能在送 delta 之前把它們沖出去。
   一批全部丟給 OT 通道、`rest` 最後才 `sync.submit()` 會讓 delta 先到伺服器
   → `BLOCK_NOT_FOUND`，或套在還沒換型別的內容上。
3. **拆出來的 delta 會被三狀態機 `compose` 進 buffer。** 上面的例子裡
   「打空白」的 `retain 1, insert " "` 與「整段覆寫」的 `delete 2`
   compose 之後變成 `delete 1` —— 那一筆不該存在的歷史就地被抵銷，
   伺服器最終內容 = 使用者所見。這是 §2.4 三狀態機本來就有的能力，
   只要別繞過它就好。

**兩道防線**（萬一還是有 `block.update{content}` 走了 tx 通道，
例如那個 block 不在本地 doc 裡、或舊版分頁）：

- `OtPageChannel.submitLocalOps()` 看到帶 `content` 的 `block.update`
  就呼叫 `dropPendingBuffer(blockId)`：outstanding 已經在線上（交給伺服器序列化），
  但 buffer 還在我們手上，必須作廢 —— 它描述的是一段不存在的歷史。
- `OtPageChannel.handleAck()` 收到「txId 不是我們這條 delta」的 ack 時，
  用 `OtClient.observeRev(rev)` 只把 rev 往前對齊、不動狀態機。
  那筆內容變更本來就已經在本地文件裡（不必 apply），但下一筆 delta 的 `baseRev`
  一定要是新的 rev，否則伺服器會拿它去和「其實已經包含在我這份內容裡」的 delta
  做 transform，offset 就歪了。

### 2.10 歷史 entry 的 op 分流規則（BUG-18）

§2.8 漏了一件事：**一筆 history entry 不一定只有內容變更。**
Enter 拆段落是 `block.update{content: 左半段}` + `block.insert{content: 右半段}`，
Backspace 合併是 `block.update{content: 合併後}` + `block.delete`，
兩者都在**同一個 transaction** 裡同時有 delta 與結構 op。

舊實作在這裡有兩個對稱的缺口（`docs/qa/functional-round4.md` BUG-18，資料遺失級）：

1. `contentDeltas()` 只要批次裡有一個非 content-only 的 op 就 `return null`
   → 那一筆 entry **完全沒有 delta 表示**
   → 收到遠端 delta 時 `rebaseStack()` 無法 transform 它，只能把它與同一條 stack 上
     依賴它的紀錄整批丟掉。redo stack 常常就這樣**整條空掉**。
2. `historyOps()` 只從 delta 生 `block.update`
   → 有 delta 的 entry 裡，`block.insert` / `block.delete` / `block.move`
     會被整個丟掉。redo 一個「拆段落」於是變成
     「把前一段的字砍掉、但不建新 block」（**再吃掉一段**）。

**規則（現行實作）**

| entry 裡的 op | 記錄 | undo / redo 時 |
|---|---|---|
| 只改 `content` 的 `block.update` | 記成 `HistoryDelta{forward, inverse}`（可 transform） | 換成「**目前**的內容 + 已 transform 的 delta」 |
| `block.insert` / `block.delete` / `block.move` | 不產生 delta，但**照樣推進中間狀態** | **原樣保留**，位置與順序不變 |
| 帶 `blockType` / `props` 的 `block.update` | 不產生 delta（型別與 props 是 LWW，§2.5） | **原樣保留**（整段 content 仍走 LWW） |

三條補充規定：

- **順序不變**：`historyOps()` 逐 op 走 `entry.ops`（redo）或 `entry.inverseOps`（undo），
  邊走邊把已產生的 op 套到一份工作用的 doc 上，所以「先 insert 再改內容」這種
  同批相依關係不會被打亂，delta 也一定以正確的中間內容為基準。
- **每個 block 只在最後一個內容 op 的位置套一次 delta**：coalesce 過的連打會在一筆 entry 裡
  留下好幾個 `block.update`，但 delta 已經被 `compose` 成一個，所以前面那幾個直接丟掉。
- **失敗時保守退回、且不動 stack**：delta 路徑不合法（block 被別人刪掉、transform 後套不上去）
  就退回整段 ops 的保守路徑；連保守路徑都套不上就回 `false`，
  **紀錄留在原本的 stack 上**。`Editor.undo()/redo()` 因此改成
  `peekUndo()/peekRedo()` → 套用成功 → `commitUndo()/commitRedo()`；
  舊的「先 pop 再套用」只要失敗一次，那一筆就被搬到錯的一邊，redo 永遠回不來。

`undo()` 與 `redo()` 走的是**同一支** `applyHistory(direction)`，
差別只有取哪一條 stack、用 `inverseOps` 還是 `ops`、以及 delta 取 `inverse` 還是 `forward`。

**回歸測試**

| 層 | 檔案 | 內容 |
|---|---|---|
| editor-core | `test/history/cross-block-redo.test.ts` | 18 條：`ot.enabled` 開 / 關各一組（不停頓連打 → Enter → 連打 → Ctrl+Z ×2 → Ctrl+Y ×2、block 中間 Enter、Ctrl+Y 與 Ctrl+Shift+Z 一致、10 次來回、undo 後打新字清空 redo stack）；協作組（遠端 delta 不清空 redo stack、undo 跨得過拆段落、Backspace 合併、別人的字不被蓋掉、ack 亂序、block 被刪掉時 redo 回 `false` 且保留紀錄） |
| e2e | `e2e/functional-round4.spec.ts` | 「BUG-18 redo 當下編輯器的狀態是正確的（跨 block，含結構 op）」——在伺服器退件之前檢查文件，跑 `--repeat-each=3` 穩定通過 |

**還沒好的那一半（不在 editor-core）**

實測（本機 vite proxy 到線上 API）確認：按下 Ctrl+Shift+Z 的**當下**，
編輯器自己的文件已經完全正確；內容是在約 1 秒後才整段消失的。原因是：

```
POST /api/pages/:id/transactions  block.insert         → 200
POST /api/pages/:id/transactions  block.delete         → 200   （undo）
POST /api/pages/:id/transactions  block.insert（同 id）→ 500 INTERNAL_ERROR   （redo）
```

`block.delete` 是 soft delete（`blocks.deleted_at`），但
`apply-transaction.ts` 的 `block.insert` 用 `findBlock()` 判斷「是否重複」，
而 `findBlock()` 帶了 `deleted_at IS NULL` —— 於是它看不到那一列，
直接走 `INSERT` 撞主鍵。「undo 刪掉、redo 插回來」是 undo/redo 最基本的形狀，
伺服器必須支援**復活**（`ON CONFLICT (id) DO UPDATE SET deleted_at = NULL, …`）。

前端收到 `txRejected` 之後 `useEditorHost` 會 `reload()`，
而 reload 是用**快取裡那份舊 snapshot** 重建編輯器 —— 這才是使用者看到的
「連前面那一段也不見了」。這兩點修好之後，
`e2e/functional-round4.spec.ts` 裡還留著 `test.fixme` 的那一條就會是綠的。

## 4. 開啟 `FEATURE_OT` 的步驟

1. **跑 migration**（新增 `blocks.rev` 與 `block_deltas`）：
   ```bash
   pnpm --filter @kennote/server migrate
   ```
2. **後端**：`.env` 設 `FEATURE_OT=true`，重啟伺服器。
   確認 `GET /api/health` 回的 `data.features.ot === true`。
3. **前端**：不用做任何事 —— 編輯器會自己問 `/api/health`，看到 `features.ot`
   就切到 delta 通道。想在開發／e2e 強制打開可以設 `VITE_FEATURE_OT=1`。
4. **驗證**：兩個瀏覽器分頁開同一頁、游標放在同一段文字，同時打字，
   兩人的字都應該保留；A 按 Cmd+Z 不應該吃掉 B 的字。

**關掉的步驟**：`FEATURE_OT=false` 重啟即可。
`text.delta` 會回 `NOT_IMPLEMENTED`，前端自動退回 M5 的 LWW 行為。
`block_deltas` 的資料留著不影響任何東西（真值一直都是 `blocks.content`）。

**前後端必須一致**：伺服器關著而前端用 `VITE_FEATURE_OT=1` 強制打開，
`text.delta` 會被拒絕，前端會收到 `onRejected` 並重抓整頁（不會壞資料，但會一直重載）。

## 5. 已知限制（誠實寫下來）

1. **undo stack 深層紀錄的 transform 是近似值。**
   對 stack 最上面那一筆是精確的（它的座標系就是目前的文件），
   更深的紀錄其座標系比遠端 delta 更舊，嚴格來說需要整條 history 的 transform 矩陣。
   實務上 undo 一定從最上面開始，所以影響很小；真的算歪了最多是 undo 的位置偏移，
   不會弄壞別人的內容（內容仍然由伺服器序列化）。
2. **OT 只作用在單一 block 內的文字。** 結構操作（新增／刪除／搬移 block）仍然是
   LWW + 冪等（04 §6.6 階段三的設計就是這樣：fractional index 讓 `insertBlock`
   之間幾乎不需要轉換）。兩人同時把同一個 block 搬到不同位置，仍然是後到者勝。
3. **與 LWW 客戶端混用**：伺服器開了 `FEATURE_OT` 但某個分頁還跑著舊版前端時，
   它會透過 `txBroadcast` 收到 `text.delta`。editor-core 的
   `transaction/apply.ts` 有一個 M2 就寫好的 `applyTextDelta()` 會處理
   retain / insert / delete，所以純文字的情況會正確；
   但它不認識 `MarkPatch` 與 `atom`，這兩種 op 會降級
   （格式不套用、atom 變成一個 U+FFFC 佔位字元）。
   **建議：開啟 `FEATURE_OT` 之後請使用者重新整理分頁。**
   反過來，舊前端送來的 `block.update{content}` 一律安全（§2.6 會把它轉成 delta）。
4. **`block_deltas` 需要保留期清理。** `pruneBlockDeltas(7)` 已經寫好但**還沒接排程**；
   在接上之前，delta log 會一直長。真值不受影響（永遠是 `blocks.content`），
   只是磁碟會慢慢變大。落後超過保留期的 client 會收到 `CONFLICT` → 重抓 snapshot。
5. **離線久了的 delta 一定會被拒絕。** 這是 OT 相對 CRDT 的本質差異（03 §8.4.4
   的比較表早就寫了）：離線編輯需要伺服器 transform，離線久了要重載。
6. **`/api/health` 的 feature 探測是每個分頁一次。** 伺服器在分頁開著的時候
   切換 `FEATURE_OT`，該分頁不會跟著切，要重新整理。
7. **IME 組字期間收到的遠端 delta 會排隊**（與 M2 的 `applyRemote` 相同機制），
   解凍後依原順序沖出去。組字很久（例如注音選字選了 10 秒）時，
   對方的字會晚 10 秒才出現在畫面上。

## 6. 替代方案與否決理由

| 方案 | 否決理由 |
|---|---|
| Yjs / Automerge | 真值會搬進二進位 doc，`blocks` 退化成投影（03 §8.4.4）；且在禁用清單上 |
| ot.js / ShareDB | 同上，且它們的 delta 格式與我們的 RichText 對不上，等於多一層轉換 |
| 為 delta 另開一組 WS 訊息型別 | 會出現第二條寫入路徑（違反 00-README 風險二的架構前置要求）；`TransactionResult.ops` 本來就是為這件事預留的 |
| 重用 `blocks.version` 當 rev | version 會因為 props / type 變更而跳號，transform 窗口會有洞 |
| `block.update{content}` 不推進 rev | 舊 baseRev 的 delta 會套在被覆蓋的內容上，offset 全錯（§2.6） |
| 客戶端讓 `block.update` 帶著 content 走 tx 通道 | 它會和 OT buffer 裡還沒送出的 delta 撞車，前綴字元被留在字尾（§2.9 / BUG-4） |
| 在 localOps handler 裡 `sync.flush()` 就想解決順序 | 救不了「被三狀態機 buffer 住」的那一筆 delta —— 它根本還沒進 tx buffer（QA 實測已回退） |
| delta 也走 300ms debounce | 會同時有多筆 outstanding，三狀態機的不變量直接壞掉 |
| 伺服器端自己寫一份 transform | OT 最常見的死法：兩邊算出不同結果就永遠不會收斂 |
| 只用單元測試 | §6.6.5 明文：「OT 極易寫錯，而且錯誤是偶爾才出現、難以重現的那種」 |

## 7. 後果

**好處**

- 兩人同時編輯同一段文字，兩人的字都保留（M6 的核心驗收標準）
- A undo 不再吃掉 B 後來打的字
- 游標不再亂跳：`transformCursor` 是精確計算，不是用 diff 猜
- 真值仍然是 `blocks.content`，搜尋 / filter / 匯出 / 版本歷史全部照舊
- `FEATURE_OT=false` 時行為與 M5 **完全相同**（同一份程式碼、同一套測試）

**代價**

- 多了一張 `block_deltas` 表與它的保留期管理
- transform / compose 的正確性靠 property test 守著，改動這一層一定要重跑 2 萬次
- 離線久了要重載（OT 的本質限制）

**M7+ 的接手點**

- `pruneBlockDeltas()` 接上 GC 排程（`gcRoutes` / `startGcScheduler` 已經存在）
- presence 的 selection 也可以用 `transformCursor` 推，讓別人的游標在我打字時不亂跳
- 結構操作的 OT（01 §6.1 的 5×5 矩陣還有幾格是 LWW），目前沒有實際需求
